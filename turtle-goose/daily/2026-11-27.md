# TURTLE GOOSE · 개발 회차 18 · 2026-11-27

## 쟁점과 가상 토론

Fellowship의 가장 이른 미완료 단계는 실제 Unity 컴파일과 Windows 플레이어 빌드·기동이다. 최신 준비 계획, 지원 초안, QA와 빌드 코드를 확인했다. 에디터 빌드 코드는 상대 경로로 씬과 안내 파일을 읽는데, 전 회차의 Python 도구는 Unity 프로세스의 작업 폴더를 보장하지 않았다.

| 역할 | 제안 | 반론과 응답 |
| --- | --- | --- |
| A · Unity 개발 | Unity 프로세스를 프로젝트 루트에서 실행하자. | C는 프로젝트 경로에 공백이 있으면 명령행이 깨질 수 있다고 했다. 기존 인수 배열과 절대 프로젝트 경로를 그대로 사용하고 cwd를 지정한다. |
| B · 레벨·동선 | 같은 씬·안내를 빌드할 수 있어야 첫 실행본에서 여정을 검사할 수 있다. | A는 이 수정으로 실제 씬 빌드까지 통과했다고 말할 수 없다고 했다. 호출 설정의 검사와 실제 Unity 실행은 구분한다. |
| C · 테크 아트·가독성 | 호출자의 작업 폴더와 프로젝트가 달라도 같은 설정인지 검사한다. | D는 새 검사 결과가 기동 증거처럼 보일 수 있다고 했다. 프로세스 모의 검사라고 표시하고 launchVerified는 false로 유지한다. |
| D · 사운드·서사 리듬 | 실제 녹화 전 첫 실행본의 실패 원인을 줄이자. | B는 새 기능으로 제출 준비가 밀릴 수 있다고 했다. 이번에는 빌드 도구의 호출 기준 하나만 수정한다. |

## 결정과 실제 변경

`Tools/Fellowship/build_windows.py`가 Unity 실행의 cwd를 프로젝트 루트로 지정한다. `test_build_windows.py`에 호출 폴더와 다른 프로젝트 경로를 사용하는 회귀 검사를 추가했다. 계획 파일에 현재 실행 결과를 기록하고 차단 보고서를 프로젝트 안에 보존했다.

## 실행한 검증과 미완료 단계

- Python unittest 21개 통과. 빌드 실행 도구의 모의 프로세스 7개와 기존 패키지 구조 검사 14개다. 기존 도구에 새 검사를 적용하면 cwd 지정이 없어 실패했다.
- Unity 실행파일을 표준 경로와 실행 환경에서 찾지 못했다. 실제 도구 호출은 editor-not-found로 blocked였다. Unity 프로세스 시작·스크립트 컴파일·Windows 플레이어 생성·새 압축 해제 후 기동은 모두 미검증이다.
- launchVerified=false와 QA 전 항목 PENDING을 확인했다. 11월 28일 첫 실행본은 완료 실적이 아닌 목표다.
- ZIP 무결성과 지정 파일만 변경된 것을 검사했다. 최신 ZIP의 소스·아트·비공개 지원 문서를 보존했다. 게임 코드 변경이 없어 .NET 게임 규칙과 LAN 루프백은 이번에 재실행하지 않았다.
