# TURTLE GOOSE · 개발 회차 04

2026-11-13 · 마지막 수로에서 친구를 기다리는 순간

## 쟁점과 가상 토론

식당에서 모와 봄을 풀어 줘도, 마지막 배 앞에 먼저 도착한 플레이어는 막연한 대기 안내만 받았다. 테라스의 실제 화면·음향 점검은 Unity 에디터를 사용할 수 없어 보류하고, 마지막 수로에서 검증할 수 있는 대기 안내를 이번 범위로 잡았다.

| 역할 | 제안 | 반론에 대한 응답 |
| --- | --- | --- |
| A · Unity 개발 | 실제 승선 반경에 들어온 동료 수를 표시하자. | C는 HUD와 승선 조건이 어긋날 수 있다고 했다. 한 카운트를 사용해 화면과 승선 가능 여부를 함께 결정한다. |
| B · 레벨·동선 | 손잡이를 돌리고 배에 다가온 다음에만 대기 숫자를 보여주자. | A는 출구까지 곧장 유도하면 수문 목표와 충돌한다고 했다. 기존 수문 잠금 및 목표 표식을 유지하고, 배 앞에서 동료를 기다리는 상태에만 붙인다. |
| C · 테크 아트·가독성 | 배에 모인 친구의 수와 전체 동행 인원을 한 줄에 표시하자. | D는 멀리 있는 동료까지 상시 표식을 띄우면 마지막 장면이 복잡해진다고 했다. 기존 상호작용 안내 한 줄을 쓰고, 전원이 모이면 승선 키 안내로 돌아간다. |
| D · 사운드·서사 리듬 | 마지막 한 마리를 기다리는 시간을 여정의 마무리로 남기자. | B는 경비 근처에서 강제 대기나 별도 효과음이 추가되면 답답해질 수 있다고 했다. 대기 시간과 소리를 추가하지 않고 기존 이동 속도와 승선 판정을 사용한다. |

## 결정과 실제 변경

- 배 앞에서 동료를 기다릴 때 **배에 모인 친구 3 / 4**와 같이 표시한다. 아구스와 화물장·식당에서 구한 보리, 모, 봄이 대상이다. 모두 기존 승선 반경에 들어오면 승선 입력이 열린다.
- `JourneyRules.cs`에서 같은 인원 수를 승선 조건에도 사용한다. `MarshHud.cs`의 수로 안내에 연결했고 `Tools/JourneyChecks/Program.cs`에 회귀 검사를 추가했다. 좌표, 저장 형식, 프리팹, 호숫가와 LAN 파일은 보존했다.

## 실행한 검증

- .NET 8 `dotnet run --project Tools/JourneyChecks` 기존 **67개**, 변경 후 **71개** 통과. 수문이 열린 체크포인트로 돌아왔을 때의 인원 재계산, 승선 반경 안팎에서 3명과 4명 구분, 아직 구출되지 않은 친구 제외를 확인했다.
- 화물장, 식당 배식종·환기구 두 경로, 두 경로에서 수문과 전원 승선, 실제 포획 후 재시도와 완료 저장 재개, 로컬 4인 LAN 루프백을 재검사했다. 새 한국어 안내의 글자가 프로젝트 폰트에 있다.
- ZIP 무결성 및 변경 대상 3개를 확인했다. Unity Play Mode, 화면에서의 안내 읽기, 실제 음향과 PC 빌드, 에디터 재시작 후 저장, 외부 플레이테스트와 실제 교체 프리팹은 미검증이다.
