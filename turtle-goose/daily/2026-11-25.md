# TURTLE GOOSE · 개발 회차 16 · 2026-11-25

## 쟁점과 가상 토론

모를 구한 체크포인트를 불러와도 새 식당 진입 때의 이야기가 나왔다. 플레이어는 이미 안에 있고 모가 동행하는데, 다시 환기구 너머의 친구들을 찾는 설명을 듣게 됐다. Unity의 새 빗장 화면 검사는 에디터가 없어 미검증으로 남겼다.

| 역할 | 제안 | 반론과 응답 |
| --- | --- | --- |
| A · Unity 개발 | 진입 자막이 현재 구조와 문 개방 상태를 읽게 하자. | B는 저장 형식을 바꾸면 이전 파일과 충돌한다고 했다. 기존 체크포인트 플래그만 사용한다. |
| B · 레벨·동선 | 모가 동행하면 빗장 단서와 봄의 구조를 이어주자. | C는 이미 옆문을 열었어도 빗장을 다시 열라고 할 수 있다고 했다. 열린 문에서는 남은 친구의 우리를 안내한다. |
| C · 테크 아트·가독성 | 기존 진입 자막 위치에 맞는 한영 문장을 사용한다. | D는 반복 설명이 길면 재시도 리듬을 해친다고 했다. 진행한 상태에서는 현재 행동만 짧게 설명한다. |
| D · 사운드·서사 리듬 | 구출한 친구와 동행을 이어가는 감각을 재시도 때도 남기자. | A는 음향까지 새로 추가하면 검증 범위가 커진다고 했다. 기존 진입 음향과 자막 시간을 사용한다. |

## 결정과 코드

`JourneyText.cs`에 현재 규칙 상태를 받는 진입 안내를 추가하고 `JourneyPlay.cs`의 진입 자막에 연결했다. 보리를 구한 화물장에서는 출구를, 모가 동행하고 옆문이 닫힌 식당에서는 모의 빗장 단서와 봄을, 문이 열렸거나 다른 친구를 먼저 구한 상태에서는 남은 목표를 안내한다. 모두 구했으면 테라스, 수문이 열렸으면 배를 안내한다.

## 실행한 검증

- .NET 8 JourneyChecks 122개 통과. `Tools/JourneyChecks/Program.cs`에서 저장값을 실제로 해석해 규칙을 생성하고, 보리 구조·모 구조와 닫힌 문·열린 문·봄 우선 구조·전원 구조·수문 개방 상태의 안내를 검사했다.
- 기존 진입 안내를 사용하는 비교 코드에서는 구조한 화물장의 출구 안내 검사가 실패했다. 빗장 개방·퇴각·재진입, 식당 두 경로, 구조·수로·포획 후 재시도·완료 저장 재개 및 4인 LAN 루프백도 회귀 검사를 통과했다.
- 새 한글 문구의 동봉 글꼴과 ZIP 무결성을 검사했다. C# 세 파일과 이 기록만 바뀌었다. Unity 화면·음향, PC 빌드, 에디터 재시작 후 실제 PlayerPrefs 저장, 외부 플레이테스트, 실제 프리팹 교체는 미검증이다.

## 추가 준비 F1 · Unity Fellowship 초점 변경

개발 16회차 이후 사용자가 요청한 제출 준비 작업이다. 새 게임 플레이 개발 17회차로 세지 않는다. 아래 대화는 이번 작업에서 작성한 가상 역할 검토이며 외부 전문가의 발언이나 심사 결과가 아니다.

### 쟁점과 가상 검토

| 역할 | 제안 | 구체적 반론과 응답 |
| --- | --- | --- |
| A · Unity 개발 | 심사자가 실행할 수 있도록 빌드 출력과 안내를 한 폴더로 내보내자. | B가 새 빌드와 실제 완주를 구분해야 한다고 지적했다. 성공한 BuildReport만 기록하고 자동 실행 검증 상태는 false로 남긴다. |
| B · 레벨·동선 | 식당 구출과 수로 탈출의 완결된 체험을 먼저 확인하자. | D가 빠른 시작만 강조하면 등껍질과 친구들의 맥락이 약해진다고 지적했다. 호숫가 시작을 유지하고 구역을 바로 볼 수 있는 기존 진입도 영문 안내에 적는다. |

### 반영한 산출물

- `FellowshipBuild.cs`: Windows/Mac용 새 리뷰 폴더 생성 코드. 실행본, 영문 안내, 글꼴 라이선스와 성공 빌드 기록을 내보낸다. 활성 플랫폼·모듈·출력 경로를 확인하고 기존 폴더를 덮어쓰지 않는다. 새 에디터 코드 자체의 Unity 컴파일·실행은 아직 확인하지 못했다.
- `Tools/Fellowship/`: 독립 실행본의 구조를 검사하고 체크섬을 포함해 ZIP으로 묶는 Python 도구와 합성 경계 검사.
- `Submission/Fellowship/`: 한국어 준비 계획, 영문 지원 답안 초안과 5만 달러 사용 계획, 영문 플레이 안내, 모두 PENDING으로 시작하는 실제 QA 검사표.
- 내부 목표: 11/28 첫 실행본, 12/04 구출 구간 완주, 12/09 아트와 4기기 플레이, 12/13 외부 테스트와 영상, 12/16 자료 정리, 12/17 제출 후보 고정. 목표 날짜이며 완료 실적이 아니다.
- 기존 오전 2시 개발 작업의 Turtle Goose 우선순위를 이 계획으로 갱신했다. CLOUD 작업 내용과 실행 시각은 유지했다.

공식 마감은 2026-12-18 14:00 PST이며, 약관 2.1(c)는 2028-03-01 이전 상용 출시 의향을 명시한다. 제작 가능 시간과 범위를 확인하기 위한 검토용 출시 목표를 2028년 2월로 잡았다. 실제 신청 폼의 질문과 분량은 아직 확인하지 않았으며 신청 접수도 하지 않았다.

### 이번에 실행한 검증과 한계

- `python3 -m unittest discover -s Tools/Fellowship -v`: 합성 Windows/Mac 폴더를 사용한 14개 검사 통과. 실행파일·DLL·데이터 누락, 실패한 빌드, 원본 프로젝트, 출력 경로와 기존 ZIP 보호, 체크섬, Mac 실행 권한, 심볼릭 링크 경계를 검사했다. 합성 폴더는 실제 Unity 플레이어가 아니다.
- 첨부에서 푼 실제 프로젝트 폴더를 패키지 도구에 넣어 소스 프로젝트로 거부하는 것도 확인했다.
- 기존 런타임 게임 스크립트 14개의 내용이 첨부 원본과 같은지 비교했다. 게임 규칙 변경은 없으며 기존 .NET 검사 122개를 이번에 다시 실행하지 않았다.
- Unity 에디터와 .NET SDK가 현재 환경에 없다. Unity 컴파일·메뉴 실행·플레이어 빌드·실제 저장 복구·4기기 대전·외부 플레이·아트 교체는 미검증이다.
- 기존 개발 점수 **75/100 유지**. 패키지 도구 추가를 플레이 품질 통과로 가점하지 않는다.
