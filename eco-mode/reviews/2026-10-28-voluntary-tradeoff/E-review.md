# E · v4 구현 준비 검토

2026-10-28. 가상 개발 자문 관점의 공개 검토다. 실제 데이터센터 개발자·시설 접근권·외부 심사자의 평가가 아니다. `rubric-v4.md`를 먼저 읽고 그 항목·배점·0/50/75/100% 단계를 적용했다. 옛 v3의 설계97/실행50을 이월하지 않았다. 이번에는 문서와 기존 코드의 관련 부분을 읽었으며 새 코드·검사·실제 모델·센서·사람 실행은 하지 않았다.

## 판단

사용자가 목적을 바꿨으므로, **자원 절감 결과를 품질 비열등성의 통과에 종속시키지 않는 것**은 타당한 연구 목표 수정이다. 성능은 별도 결과로 계속 측정한다. 옛 IUT 공동규칙을 그대로 두고 이름만 v4로 바꾸면 구현과 새 질문이 충돌한다.

기존 `analysis_prepare.py`는 `numeric_joint_rule`을 에너지 규칙과 품질 규칙의 결합으로 계산한다. 이는 v3 준비 도구의 의미를 보존해야 하며 v4의 성공 판정에 그대로 호출하지 않는다. 기존 `session_replay.py`의 `response_observation`은 평탄한 합성 schema에서 reasoning 필드 하나를 확인하는 helper이다. v4에서 요구하는 실제 provider usage·캐시·입출력 포함관계 adapter가 완성된 증거가 아니다.

개발용 scorer는 품질을 별도 결과로 측정하는 도구의 일부로 재사용할 수 있다. 그러나 신뢰된 로컬 함수용이며 비신뢰 산출물 격리·UI/서버·실제 모델/센서 연결을 제공하지 않는다. 기존39/1087 실행은 이 검토에서 새로 수행한 검사가 아니다.

## 구체적으로 보완할 명세

### 1. 토큰은 포함관계가 확인된 지표별로 기록한다

각 token metric에 다음 계보를 연결할 것을 권고한다.

| 필드 | 의미 |
|---|---|
| `value`, `unit` | 값과 단위. 미제공은 null이며 관측0과 구별 |
| `source_field`, `schema_version` | 원본 응답 필드와 그 의미를 고정한 provider/runtime 버전 |
| `inclusion_scope` | 입력/추론/최종 답변/완료/전체/캐시 포함관계 |
| `completeness`, `missing_reason` | 완전·부분·미제공·충돌과 이유 |
| `source_event_id`, `attempt_id` | 원본 사건과 실제 서버 실행의 연결 |

논리적 전체 input 문맥, 실제 처리된 uncached/cached 항목, provider의 청구 단위는 구별한다. reasoning이 completion에 이미 포함되어 있으면 다시 더하지 않는다. cached input이 input의 subset이면 input에 덧붙이지 않는다. provider가 지원하지 않는 내부 reasoning을 화면의 답변 텍스트 재토큰화로 복원했다고 하지 않는다. 청구금액은 연산 토큰 총량이나 전력 측정값이 아니다.

세션의 ‘총토큰’은 포함관계와 집계 단위가 확인된 경우에만 이름과 식을 고정한다. 같은 문맥이 실제 재요청으로 다시 처리되면 그 실행의 사용량을 보존하며, 최종 대화문 한 번의 길이로 전체 반복 사용량을 대체하지 않는다. 서로 다른 metric을 임의 가중해 하나의 보편 compute 지수로 만들지 않는다.

### 2. 실제 재실행과 로그 재전송을 구별한다

assignment → session/task → logical request → backend attempt의 ID를 구분한다. 같은 요청에 서버가 실제로 다시 실행한 retry는 별도 attempt 비용으로 포함한다. 전송만 재시도한 동일 telemetry는 사건 ID와 payload를 대조해 중복 제거하고, 서로 충돌하면 raw를 보존한 채 해당 집계를 unknown으로 표시한다.

같은 attempt의 권위 있는 final cumulative usage가 있다면 streaming chunk 누적값과 다시 합산하지 않는다. 어떤 원본을 권위 있게 채택할지는 provider/runtime별 근거와 함께 사전 고정한다. 잠금·취소 이후 늦게 도착한 usage는 원래 attempt에 연결하고 원본을 보존한다. 취소·연결 끊김으로 usage가 없으면 0으로 바꾸지 않는다. 실제 일부 실행 비용은 있었어도 전체값은 미확인일 수 있다.

부분값을 신뢰할 수 있는 하한으로 보고하려면 ID·단위·포함관계·중복·실행 귀속이 유효해야 한다. 선언된 input만으로 진위나 하한 유효성을 인증하지 않는다.

### 3. 토큰 완전성과 에너지 유효성은 별도로 판단한다

`token_completeness`와 `energy_measurement_validity`는 서로 대체하지 않는다. 모든 token usage가 있어도 J가 없을 수 있고, 유효한 세션 J가 있어도 내부 reasoning 수가 미제공일 수 있다. 토큰 감소/J 증가 결과를 숨기지 않는다. 토큰 환산으로 센서 null을 채우지 않는다.

J의 계보에는 기존 측정 source/device/scope/epoch/unit, raw counter 양끝, read bracket, reset/staleness 근거, task lock·backend-drained 참조, 타 작업/세션 중첩과 누락 사유를 연결한다. 미확인 근거는 null과 이유로 남긴다. 작업 중 운영상 공개 피드백과 연구용 사후 채점은 stage와 계측 경계를 구별하며 이중 합산하지 않는다.

환경 영향은 측정 경계 안의 J, 위치·시간 등 자료로 조건 추정한 탄소/물, 이번 자료로 확인할 수 없는 자연 훼손 방지 전체를 구별한다. 향후 영수증 UI를 만든다고 환경 보증이 생기는 것은 아니다. 이번 연구에 새 영수증 기능을 필수 추가하지 않는다.

### 4. 성과·선택·이해·수용은 다른 기록이다

최종 불변 산출물과 성공·실패·포기·unknown을 모든 배정 분모에 유지한다. 성능이 낮아진 것을 환경 때문에 자발적으로 감수했다는 증거로 자동 변환하지 않는다. 공통 안내 제공, 이해, 사후 수용 보고, 환경 이익 인식, 객관 성과는 별개 자료다. 사후 수용 보고로 주 분석 표본을 선별하지 않는다.

자원 감소를 보고하는 데 NI 통과를 요구하지 않는 대신, 성과와 미완수도 함께 보고한다. 덜 완수해서 소비가 줄었다는 결과 역시 보존하되 같은 일을 더 효율적으로 했다는 주장과 구별한다.

### 5. 실행 이행안

1. v4의 핵심 결과·비교·집계식·누락 규칙을 먼저 동결한다. 기존 v3 분석과 파일/버전/출력 의미를 구별한다.
2. 실제로 택할 provider/runtime의 raw response·usage·effective budget와 종료 trace에 맞는 adapter를 구현하고, 정상·취소·재전송·서버 재실행·필드 누락·schema 변경을 확인한다.
3. 토큰 집계와 세션 J를 독립 감사하고 최종 산출물에 연결한다. UI와 서비스가 실제 사건을 생성하는 경로를 검증한다.
4. 실제 자료가 확보되기 전 `confirmatory_allowed=false`를 유지한다. 이번 문서가 위 구현을 완료했다는 표시를 하지 않는다.

장비 질문·구매·유료 사용을 지금 요청하지 않는다. 실제 실행 단계의 접근권·계측·비용 근거는 나중에 확인해야 하는 미충족 조건으로 보존한다.
