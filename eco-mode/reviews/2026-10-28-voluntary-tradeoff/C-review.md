# C · v4 자발적 성능 교환과 실제 토큰의 검토

2026-10-28. C는 AI 기술의 가상 검토 관점이며 외부 교수·실제 모델 운영자의 권한을 뜻하지 않는다. 이번에는 v4 초안·F 역할 정의·점수 부여 전에 고정한 v4 기준과 기존 개발 코드 명세를 읽고 D·E·F·A와 공개 논점을 교환했다. 새 모델 추론·센서·참가자·코드 검사는 실행하지 않았다. 이 문서의 점수는 새 v4 초안의 준비도이며, 옛 C 설계100을 이월하지 않는다.

## 1. 사용자 목표에 대한 판단

**품질 비열등성을 자원 절감 결과의 필수 성공 관문에서 제거하는 수정에 동의한다.** 사용자가 성능이 낮아질 가능성을 받아들이는 상황도 연구할 수 있다. 다만 저예산이라는 설정과 낮은 실제 성능은 동의어가 아니며, 연구자가 일부러 오답을 삽입할 이유도 없다. 저예산은 실제로 적용한 연산 설정으로 정의하고, 최종 성과는 측정하는 교환 결과로 남긴다.

‘성능 저하 가능성을 안내받음’, ‘이해함’, ‘실제 낮은 설정 선택’, ‘손해를 수용했다고 사후 말함’, ‘객관적 성과가 낮아짐’은 다르다. 사용자가 환경을 고려했다고 말한 자료는 중요한 보고지만, 그것만으로 환경 동기가 선택의 인과 원인이었다고 확정하지 않는다.

세 표시 집단에 공통으로 제시할 성능 안내는 ‘일부 과제에서 정확도가 낮아지거나 오류가 늘 수 있다’는 후보 문구로 제한한다. Low가 항상 나쁘다거나 Eco가 절약한다는 보증을 붙이지 않는다. 실제 설정의 제어·관련 성능 자료·안내 이해도가 확인되기 전에는 참가자용 안내가 검증됐다고 하지 않는다.

## 2. 두 라운드 공개 교환 요약

다음은 이번에 실제 전달한 방법 논점을 정리한 공개 요약이다. native 계정 export나 시각이 보존된 원문 전사가 아니다. 가상 발언은 실제 사용자의 새 승인과 구별한다.

### D와의 교환

**D 1라운드:** completion/total에 reasoning이 이미 들어가면 다시 더하지 말아야 하며, cached input의 노출·실제 처리·billing을 구분해야 한다. 사용량 누락은0이 아니다. 포기 증가로 J가 줄어도 같은 성과의 효율 향상이라고 부를 수 없다.

**C 1라운드:** 이 구분에 동의했다. logical context, 실제 processed input, billing 계수는 별개다. 내부 값이 미제공이면 unknown이며, visible text를 다시 토큰화한 값으로 내부 추론이나 처리량을 복원했다고 하지 않는다. 성과는 필수 성공 관문에서 제외하지만 완료율·실패와 함께 결과로 보고한다. 토큰 감소와 J 증가의 불일치도 기여 후보로 수용할 수 있는지 D에게 물었다.

**D 2라운드:** 불일치도 사용자가 생각한 절약과 물리적 소비가 어긋나는 조건을 보여주는 결과 후보로 수용했다. J 증가 역시 환경 전체 악화를 곧바로 증명하지 않으며, 측정 경계·전력원·시간·냉각 등을 분리해야 한다. 장기 총수요·반동은 후속 범위다.

**C 반영:** 토큰, 측정 J, 조건부 환경 추정은 서로 다른 결과로 남기고, 어느 하나의 부호를 다른 결과로 대체하지 않는다.

### E와의 교환

**E 1라운드:** request와 backend attempt를 구분하고 usage 필드의 포함관계·캐시·billing을 먼저 정의해야 한다. 중단·전송 유실의 usage 부재는 unknown이다.

**C 1라운드:** 필요한 근거는 provider/runtime/version별 raw usage 구조, 각 필드의 포함관계, intended/effective budget 및 종료 trace다. 마지막 usage가 권위 있는 누적값이면 stream chunk와 중복 합산하지 않도록 제안했다. 각 metric에 value/unit/source_field/schema_version/inclusion_scope/completeness를 연결하는 명세를 E에게 물었다.

**E 2라운드:** 위 필드에 source_event_id/attempt_id를 더하는 안에 동의했다. 같은 attempt의 final cumulative usage는 한 번 채택하며 재전송은 ID와 payload로 대조한다. 충돌은 raw를 보존하고 unknown으로 남긴다. 별도 backend 재실행은 새 attempt로 포함하고, 늦은 usage는 원래 attempt에 연결한다. 기존 평탄 fixture helper는 실제 adapter 검증이 아니다.

**C 2라운드:** 제안을 수용했다. 미제공 reasoning과 관측된0 reasoning을 구별하고, 없는 내부 필드를 visible answer 토큰으로 채우지 않는다. 이 명세를 실제 adapter 구현·검증으로 승격하지 않으므로 토큰 기준은 부분 점수다.

### F · 안종훈 가상 역할과의 교환

**C 1라운드:** 품질 유지를 필수 관문에서 제외할 수 있지만, 낮은 성능을 모든 과제의 정의로 만들거나 일부러 성능을 떨어뜨릴 필요는 없다고 제안했다. 예상·이해·선택·수용 보고·실제 성과를 분리하는 방식이 사용자 견해를 충실히 반영하는지 물었다.

**F 1라운드:** 토큰 절감과 자연을 아끼는지가 질문이며, 성능 저하를 받아들일 수 있다는 뜻이지 모든 과제에서 반드시 성능이 낮아야 하는 것은 아니라고 답했다. 토큰 결과 자체의 의미를 보존하려면 무엇을 보고해야 하는지 물었다.

**C 2라운드:** 지원되는 input·cached subset·generated total·reasoning subset·visible answer를 뜻에 맞게 분리하고, 재질문·상향 전환을 포함한 전체 backend attempts를 보존하겠다고 답했다. 토큰 감소 자체는 의미 있는 사용 결과이며, J 감소가 확인되지 않았다는 이유만으로 연구 전체가 무의미해지는 것은 아니다.

**F 2라운드:** 토큰 감소/J 증가 또는 불확실한 J도 중요한 결과가 될 수 있다는 구분을 수용했다. 성능 저하는 예상·허용 가능성으로 두고 실제 성과를 함께 측정하며, 사후 환경 동기 보고와 인과 원인의 증명을 구별하기로 했다. F의 답변은 실제 사용자의 새 승인이 아니다.

### A와의 추가 조율

A가 ‘성능 저하 가능성의 공통 안내’와 ‘실제 성과 측정’을 구분하고 오답을 섞는 품질 조작을 하지 않겠다는 제안을 보냈다. C는 low/high를 실제 연산 설정으로 정의하고, 사실성 확인 전 공통 안내는 후보 상태라는 점에 동의했다. 객관적 성과를 토큰/J 결과의 성공 전제로 요구하지 않는다.

## 3. v4에 반영할 토큰 명세

아래는 실제 provider 필드명이 아니라 **지원되는 값에만 적용할 의미 구분**이다. 선택할 provider/runtime와 응답 스키마가 확정되기 전 모든 필드를 얻을 수 있다고 약속하지 않는다.

| 구분 | 필요한 정의와 주의 |
|---|---|
| 논리적 입력 문맥 | 요청에 담긴 전체 문맥의 토큰 수. 그만큼 매번 새로 연산했다는 뜻은 아니다. |
| 실제 제공된 input usage | provider가 무엇을 포함해 보고했는지 스키마·버전과 함께 기록. 논리적 문맥과 같다고 가정하지 않는다. |
| cached input | input의 부분집합인지 별도 항목인지 확인. 캐시 할인 요금이 같은 비율의 연산·J 절감이라는 뜻은 아니다. |
| generated/completion total | 내부 추론·도구 호출·최종 텍스트 등을 무엇까지 포함하는지 확인. 정의를 모르면 범용 total로 합치지 않는다. |
| reasoning usage | completion total의 부분집합이면 그 total에 다시 더하지 않는다. 미제공은0이 아니다. |
| visible answer tokens | 토크나이저/버전과 계산 경로를 명시할 수 있는 보조 값. visible answer 재토큰화는 숨은 추론이나 실제 처리량의 복원이 아니다. |
| billing | 가격·할인으로 가중된 요금 산출과 사용량 계수를 별도로 보고. 청구 금액 감소를 실제 총토큰/J 감소로 대체하지 않는다. |

각 계수는 value, unit, source_field, schema_version, inclusion_scope, completeness, source_event_id, attempt_id를 가진다. 누락과 관측0을 분리한다. stream chunk, final cumulative usage, 재전송, 실제 재실행의 우선순위·중복 제거 규칙을 사전에 정한다. request와 attempt를 바꿔 세지 않는다. 확정된 값만 합산하며 전체 합계가 불완전하면 완전한 총량으로 표시하지 않는다.

## 4. 고정 v4 기준에 따른 첫 준비도 평가

평가 대상은 `protocol-v4-draft.md`와 이번 공개 제안이 있는 상태다. 아직 통합되지 않은 제안을 구현 완료로 채점하지 않았다. 각 항목은 사전에 고정된0/50/75/100% 단계만 사용했다.

| 고정 C 항목 | 배점 | 단계 | 점수 | 확인 근거와 남은 결손 |
|---|---:|---:|---:|---|
| 실제 두 설정 | 25 | 50% | 12.5 | 의도 설정·실제 적용·종료 trace를 구별하는 명세가 있다. 실제 두 예산이 적용된 모델 실행 자료는 없다. |
| 토큰 정의 | 25 | 50% | 12.5 | 중복 합산·캐시·billing·누락의 구분과 계보 제안이 있다. 기존 response_observation은 평탄 fixture helper이며 실제 provider adapter·raw 응답 검증이 없다. |
| 성과/실패 | 20 | 75% | 15 | 품질을 성능 교환의 결과로 유지하고 전체 배정 분모·unknown을 보존한다. 신뢰된 개발 계약·채점 검사 기록은 있으나 최종 과제/사람/모델 산출물 평가가 없다. |
| 작업/일반화 | 15 | 75% | 11.25 | 작업 종류·충분성·high 기준 충족과 일반화 범위를 구별한다. 최종 작업·독립 성능 자료·분류는 미정이다. |
| 기술 검증 | 15 | 0% | 0 | v4 대상 시스템의 실제 모델·usage adapter·센서/로그 연결 실행 증거가 없다. 개발 fixture 실행은 이 요건의 대체가 아니다. |
| 합계 | 100 |  | **51.25** | **v4의 첫 준비도 점수이며, v3의 C 설계100과 다른 목표·범위다.** |

점수 하락은 사용자의 생각이 잘못됐다는 뜻이 아니다. 실제 토큰·에너지 절감을 물으려면 어떤 실행 근거가 아직 없는지를 드러낸다. 동일 품질 유지의 관문을 삭제했다고 실제 설정·측정의 요건까지 사라지지 않는다. 모든 역할의100을 문서 토론만으로 선언하지 않는다.

## 5. 현재 수행 범위

이번 C는 파일 읽기와 공개 조율·명세 검토만 했다. 기존 검사 수62/35/39/1,087을 새로 실행하거나 더한 것이 아니다. 실제 LLM·센서·참가자 결과, 최종 usage 스키마·p_min·표본·환경 영향 값은 만들지 않았다. 장비 질문은 보류했고 `confirmatory_allowed=false`를 유지한다.

## 6. 통합본 최종 확인

총괄이 작성한 `research/protocol-v4.md`를 한 번 읽고 위 고정 기준으로 다시 확인했다. 토큰 일곱 구분, metric 계보, stream/final usage와 실제 재실행의 중복 구분, 누락을0으로 채우지 않는 규칙, 성능 저하를 강제하지 않는 안내, 객관 성과를 필수 성공 관문에서 제외하는 변경이 반영돼 있다. 또한 안내받음과 실제 이해·수용을 구별하고 모든 원배정 참가자의 명칭 총효과를 주 추정대상으로 명시했다. 문서의 기술적 해석에 추가 결격은 발견하지 않았다.

이것은 **통합 문서의 확인**이며 실제 provider adapter·effective budget·토큰/계측 연결 검증이 아니다. 새 실행 근거가 없으므로 항목 점수를 올리지 않는다.
