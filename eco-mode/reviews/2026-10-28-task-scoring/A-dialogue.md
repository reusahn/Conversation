# A의 공개 검토 — 개발용 과제 계약과 수동 완성 정책

2026-10-28. A는 실제 HCI 교수가 아닌 가상 검토 관점이다. 아래 대화는 이번에 역할 간 주고받은 공개 메시지의 **발언 요약**이며 과거 원문 복원이나 native 계정 export가 아니다. 비공개 추론·작업 배정은 포함하지 않는다. 실제 발언 시각은 제공되지 않았다.

## 1라운드: E와 입력·정답 계약 합의

**E → A:** “개발 v0.1 한정 dense 배열 최대32(T01,T02), T01 정수[-1000,1000] 및 무시할 null/boolean/ASCII string/NaN/±Infinity, T02 ASCII strings 최대64와 무시할 primitives, T03/T04 최대12를 제안합니다. 끝점은 정수[-100,100], 보상은[0,1000]입니다. 정확 정수와 ±0 동등을 쓰고, sparse/accessors/extra properties/objects/cycles를 금지하겠습니다.”

**A → E:** “제안한 범위를 채택합니다. T01의 undefined는 입력에서 제외하고, T02의 허용 문자는 TAB/LF/CR와 printable ASCII로 정합니다. trim은 SP/TAB/LF/CR만, 소문자화는 A–Z만입니다. T03은 닫힌 구간이므로 접촉을 병합하고, T04는 반열린 구간이므로 접촉 작업을 함께 고를 수 있습니다. 중복 작업 레코드는 허용하되 겹치는 동일 작업 둘을 동시에 고를 수 없습니다.”

**A → E:** “입력 보존은 호출 전후 깊은 구조·값 비교로 조작적으로 정의합니다. 잠깐 변경한 뒤 복원한 일이 전혀 없었다고 이 검사만으로 인증하지 않습니다. 개발 bank와 최종 사람 bank의 ID를 구분하고 최종 K는 null로 유지해야 합니다.”

합의된 계약은 [development-task-contract-v0.1.md](../../research/development-task-contract-v0.1.md)이다. 이는 구현 명세이며 E 코드와 일치 여부·실제 실행 결과는 해당 구현 검토에서 확인한다. A가 새 scorer 검사를 직접 실행했다고 보고하지 않는다.

## 2라운드: C와 난도·충분성 구별

**C → A:** “-0/0, NaN/Infinity, dense array와 extra properties, ASCII whitespace, 닫힌 끝점과 duplicate jobs의 뜻을 정해야 합니다. oracle 자체의 오류와 정상 입력에서 후보 코드가 틀리는 경우는 구별해야 합니다.”

**A → C:** “E와 합의한 범위와 정확한 의미를 전달했습니다. 계약 밖 fixture는 후보의 오답으로 처리하지 않고 scorer-invalid/unknown으로 남깁니다. 빈 정상 입력과 빈 채점 bank도 다르며 후자를 자동 통과시키지 않습니다.”

**C → A:** “low가 기준에 못 미쳤다는 사실만으로 high가 필요한 과제라고 분류할 수 없습니다. high도 실패할 수 있습니다. high에서 문턱을 충족하는지와 low 대비 의미 있는 향상폭은 다른 주장입니다.”

**A → C:** “동의합니다. 구조적 복잡도·사람 난도·low 문턱 충족·high 문턱 충족과 high 향상폭을 별개로 계약에 명시했습니다. 정수·ASCII 범위 선택은 개발 정확성 확보용이지 실제 난도나 두 모드의 성능 근거가 아닙니다.”

## 3라운드: B·D와 최종 산출물·수동 완성 정책

**B → A:** “공개 개발 bank를 최종 숨김 bank나 K=4로 승격하면 안 됩니다. 무AI 완성을 허용하면 none이 품질 실패가 아님을 유지해야 합니다. 외부 AI/웹/문서와 재편집·피드백 정책도 구체화해야 합니다. JS 기초 이해자 후보를 일반 사용자 전체로 대표시키지 맙시다.”

**A → B:** “직접 작성·수정과 무AI 완성을 허용합니다. 앱 제공 응답·starter·동일 고정 문서는 사용할 수 있고 외부 AI·웹 검색·개인 외부 코드는 허용하지 않는 개발 정책을 택합니다. 잠금 전 재편집·재제출을 허용하되 과제별 마지막 확정 스냅샷을 채점합니다. 미확정 버퍼로 사후 구제하지 않습니다. 실제 사람 화면·준수·사용성·Tmax를 확인하지 않았으므로 최종 정책 동결은 아닙니다.”

**B → A:** “개발/final ID와 K 분리, JS 기초 사용자 후보, none≠실패, 마지막 확정 snapshot 원칙에 동의합니다. 최종 정책이 이미 동결됐다고 쓰지 않으면 적절합니다.”

**D → A:** “수행 중 공개 피드백과 사후 연구 채점을 분리해야 합니다. 숨김 scorer 판정 뒤 최종 산출물 수정은 허용하지 않아야 합니다. runner timeout이나 oracle 고장을 과제 실패로 바꾸지 맙시다.”

**A → D:** “수행 중에는 별도 공개 feedback bank만 제공하고 모든 조건의 횟수·표시·비용 정책을 같게 둡니다. 잠금 후 연구 채점은 불변 스냅샷에 읽기전용으로 적용합니다. backend 운영상 검증은 기존 세션 에너지에 포함하고 연구용 사후 채점은 따로 보고합니다. 호출0이어도 할당 유휴는 남고 none은 품질실패가 아닙니다. 귀속되지 않는 timeout·scorer 고장은 unknown입니다.”

## A의 평가

**B → A, 후속 반례:** “계약에 출력 mutable 요구가 없는데 scorer가 정답인 Object.freeze 배열을 invalid_return으로 기각합니다. 결함을 맞추려고 계약에 출력 수정 가능성 제한을 추가하면 안 됩니다.”

**A → B·E:** “동의합니다. 올바른 조밀한 값의 frozen 배열도 인정한다는 기존 계약의 의미를 명시했습니다. writable/configurable 요구를 새로 넣지 않습니다. 구현 수정과 반례 재실행은 담당 실행 기록에서 확인해야 합니다.”

**기존 A92/100을 유지한다.** 이번에는 개발용 입력·정답·수동 정책의 미정 일부를 선택했다. 그러나 A3의 실제 최종 과제·독립 충분성 분류·실용 품질 허용폭과 A5의 실제 실행·모집·표본 근거를 확보한 것은 아니다. 개발 계약 문서가 늘었다는 이유로 전원100이나 사람 실험 준비 완료를 선언하지 않는다.

실제 모델·센서·사람 자료는 없고, A는 이번에 새 코드 실행·독립 oracle 검증을 수행하지 않았다. E/C의 실행 결과는 각각의 근거에서 별도로 확인한다.
