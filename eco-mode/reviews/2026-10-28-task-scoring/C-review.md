# C 공개 검토 — 개발 채점기의 독립 반례와 오라클 대조

2026-10-28. C는 가상 AI 자문 관점이며 외부 교수의 심사·시설 인증이 아니다. 실제 모델·센서·사람 실험을 수행하지 않았다. 신뢰된 로컬 JavaScript 함수와 공개 개발 bank만 실행했다. E가 시작한 구현의 최종 정리는 부모 도우미가 이어받았다. E의 최종 재심사나 실행 완료 점수를 대신 생성하지 않는다.

## 공개 질의와 응답 요지

**C → A·E:** “정상 입력에서 후보가 틀린 값을 내거나 예외를 내는 것과, fixture·oracle·설정이 깨진 것을 분리해야 합니다. ±0, sparse array, ASCII 공백, 닫힌 구간과 반열린 작업 구간도 명시해야 합니다.”

**A·E → C:** “조밀한 ordinary 입력 배열, bounded 정수, 제한 ASCII를 개발 계약으로 채택합니다. 숫자 정답에서 ±0은 동등합니다. 입력 보존은 호출 전후의 값·구조 검사이고, 임시 변경 후 복원 부재까지 인증하지 않습니다. 입력·bank·oracle 고장은 unknown입니다.”

**C → E:** “`options=null`이면 후보의 오답이 아니라 채점기 호출 설정 오류입니다. 설정을 읽는 중 예외가 runner 밖으로 탈출해서는 안 됩니다.”

**B → C·E:** “입력용 배열 검증을 출력에 재사용하면 frozen 상태인 올바른 출력도 실패할 수 있습니다.”

**C → 부모:** “정상 T02 출력 배열과 정상 T03 외부·중첩 배열을 freeze한 반례를 직접 실행했고 모두 invalid_return으로 실패했습니다. 출력 mutability를 요구하지 않는 계약에서는 false failure입니다.”

위는 실제 주고받은 공개 메시지의 요약이며 native 계정 export·원문 시각을 주장하지 않는다.

## 실제 재현한 결함

1. **잘못된 옵션의 unhandled 예외:** 초기 `scoreSolution('T01',reference,undefined,null)`가 `TypeError: Cannot read properties of null (reading 'oracle')`를 runner 밖으로 던졌다. E가 옵션을 검증하도록 수정한 뒤 같은 입력이 unknown이 됨을 직접 확인했다.
2. **읽기전용 정상 출력의 오채점:** scorer SHA-256 `d08dc674eacd725a4d180273a304a66e2ac3bb6cec70aad7a63c1e2f879c7d73`에서 frozen T02/T03 정상 답이 observed_failure/invalid_return이었다. C 회귀 검사에 두 정상 출력의 success 요구를 추가한 버전은 실제 exit code 1로 실패했다. 부모가 입력·출력의 mutability 요구를 분리한 후 회귀 검사가 통과했다.

3. **비열거형 정상 출력의 오채점:** frozen 수정 뒤에도 T02 정상 반환 배열의 숫자 인덱스 속성을 `enumerable:false`로만 바꾸면 6개 case가 실패했다. 출력 계약은 이 descriptor 특성을 요구하지 않는다. 부모에게 직접 재현 결과를 전달했고, 부모가 출력의 열거가능성 요구도 분리했다. 최종 C 검사는 T02와 중첩 T03의 비열거형 정상 출력을 한 회귀 항목으로 포함해 모두 통과했다. 입력 배열의 mutability·열거가능성 검사는 그대로 유지했다.

## 독립 대조의 방법

오라클을 자기 자신으로 재검사하지 않도록 다른 계산 방식을 사용했다.

| 과제 | C의 비교 방식 | 입력 수 |
|---|---|---:|
| T01 | BigInt로 유한 정수를 정확 합산한 뒤 Number로 변환 | 256 |
| T02 | 제한 ASCII의 정규식 양끝 공백 제거·native lowercase·배열 중복 검사 | 256 |
| T03 | 작은 좌표계의 half-grid 점유로 연속 구간을 복원. 점구간 사이 실수 빈틈을 구분 | 261 |
| T04 | 종료시각 정렬의 가중 일정 DP. E 오라클의 부분집합·쌍별 양립 검사와 대조 | 257 |
| 합계 | 유한 결정론적 입력에서 오라클 값 대조 | 1,030 |

추가 검사는 alternate 정상 알고리즘, 빈 정상 입력, 후보 예외·thenable·Promise 거부, 잘못된 fixture·bank·oracle, 외부·중첩·prototype mutation, ±0, readonly 출력의 상태를 확인한다. 입력 1,030개는 참가자·LLM 표본이 아니다. 기본 E/부모 검사와 중복될 수 있어 독립적인 연구 표본 수나 포괄 coverage로 합산하지 않는다.

## 두 추론 설정의 과제 분류에 대한 공개 반론

low가 문턱을 못 넘었다고 high가 도움 된다고 할 수는 없다. high도 실패할 수 있다. 독립 벤치의 task×mode 전체에 대한 동시 포함 사건 아래, `U_low < p_min`과 `L_high >= p_min`을 함께 충족하면 ‘고정한 두 모드 중 high에서 문턱을 충족한 과제’라고 구별할 수 있다. 이를 모든 대안에 high가 필수라는 주장으로 확대하지 않는다.

또한 문턱을 넘었다는 것과 사전 실용 향상폭을 초과했다는 것은 다르다. 후자를 주장하려면 차이 하한과 사전 향상폭 기준이 별도로 필요하다. 이번에는 임의의 향상폭을 추가하지 않고 문턱 분류 용어로 제한하는 방안을 권고했다. 실제 독립 벤치·p_min·분류·RQ3 효과는 아직 없다.

부모가 통합한 `research/task-strata-correction-v0.1.md`를 직접 읽었다. 네 범주의 상호배타성, 경계의 strict 부등호, high 단조성 비가정, task×mode 전체 양측 구간의 union bound와 꼬리 오류배분, unknown 보존, RQ3 탐색 조건이 위 반론과 일치한다. 수학적 논리의 문서 검토이며 새 통계 코드 실행이나 실제 분류는 아니다.

## 평가와 한계

기존 C 설계100을 유지한다. 발견한 개발 구현 결함은 위 범위에서 수정·재검사했으며, 기존 C의 설계 기준을 낮추거나 새 실행 점수를 만들어 만점을 선언하지 않는다. 실제 모델 예산 제어·과제 타당화·센서·사람 반응·환경 개선을 인증한 점수가 아니다.

이 채점기는 신뢰된 동기 로컬 함수만을 대상으로 하며 실행 격리·timeout·전역 상태 오염 방어·임의 악성 Proxy 방어를 제공하지 않는다. 참가자나 외부 모델이 낸 임의 코드를 이 프로세스에 넣는 경로로 사용하면 안 된다. 현재 공개 bank는 최종 숨김 bank가 아니다. shape가 정상인 의미적으로 틀린 oracle을 자동 판별하는 완전한 장치도 아니다. 오라클의 throw·잘못된 shape·입력 변이는 탐지하지만, 독립 유한 대조가 모든 입력의 수학적 정확성을 증명하지는 않는다. `confirmatory_allowed=false`를 유지한다.
