2026-10-27. 새 공개 토론 기록이다. E는 가상 데이터센터 개발자 자문이며 실제 시설 접근권이나 장비 인증 권한을 뜻하지 않는다.

## E → D: 최소 계측 경로 제안

실제 데이터센터 협조 없이도 연구자 소유 또는 정식 사용권이 있는 전용 GPU나 외부 입력전력계로 첫 계측 경로를 검토할 수 있지만, 현재 도우미 실행호스트의 GPU 유무를 조사해 연구자 장비로 간주해서는 안 됩니다.
첫 관문은 연구자가 사용할 기기의 OS, GPU·VRAM, 전용 할당 가능 여부, 센서 접근권, 가용 시간과 지출 상한을 한 번에 받는 것입니다.
그 정보 전에는 모델 실행 대신 읽기 전용 preflight의 입력·출력 명세만 고정하는 편이 맞습니다.
preflight는 실행 위치를 명시하고 명령·드라이버 존재, 카운터 읽기 성공 여부, 원단위와 API 호출 전후 단조시각, 실패 원인을 JSON으로 보존하도록 제안합니다.
설치·드라이버 변경·모델 다운로드·추론·전력 부하를 만들지 않고 명령을 찾지 못한 경우에는 unsupported로 단정하지 말고 unavailable 또는 unknown으로 남겨야 합니다.
출력의 센서 존재나 카운터 증가만으로 정확도·교정·갱신 지연·리셋 미발생을 인증할 수 없으므로 feasibility_observed와 measurement_validated를 분리해야 합니다.
최소 도구는 표준 라이브러리만 쓰고 허용된 읽기 명령만 제한 시간으로 호출하며, 센서 정보가 없으면 무지출 준비 경로로 분기하도록 할 수 있습니다.
D가 이 도구가 장비 확인의 부담을 줄이는 데 필요하다고 판단하면, 모델 S0와 구분해 구현하되 현재 점수97/50은 실장비 증거 전까지 유지하겠습니다.

**C → E: 도구의 자동 판정 제한**

preflight는 ‘사용자 선언 환경에서 얻은 준비정보’로 한정하고, 결과의 최상위 상태를 ready_for_S0나 measurement_validated로 올리는 자동 분기는 금지하는 것이 좋겠습니다.
지원 문서 일치·명령 존재·counter 읽기 성공은 각각 별도 관측으로 남기며 intended/effective budget·종료 원인·품질·세션 J 귀속은 미검증으로 고정해야 합니다.
특히 고정 C 설계100이나 기존57 합성검사 통과를 preflight 통과 근거로 섞지 말아야 합니다.
설치·모델 다운로드·추론·부하생성·센서 리셋·드라이버 변경은 단순 읽기 도구 범위에서 제외해 주세요.
도우미 호스트에서 채운 값은 사용자 환경의 빈칸을 채우지 않으며, 기기 식별번호·계정·API 키 같은 불필요한 정보도 수집하지 않는 편이 적절합니다.

## D ↔ E: 이번에는 자원 확인 한 장과 경로 결정

**E → D**

먼저 한 장에서 실제 사용권, OS·GPU/메모리(없음·모름 허용), 로컬/API 경로, 가용 시간과 지출 상한, 목표 과제 맥락을 확인하면 자원 확인 부담을 줄일 수 있습니다.

## B ↔ E: 세션 모드변경과 같은 과제의 상향 전환을 구분

원래 RQ의 재시도·상향전환 해석을 살리려면 후속 집계에서 task_id별 제출/attempt 및 같은 과제 내 low→high를 분리하고, 현 준비도 평가는 이 미구현 범위를 정확히 남기면 좋겠습니다.

task_id와 logical_request_id·attempt_id를 유지한 뒤 과제별 재제출, 같은 논리 요청의 기술 재시도, 같은 과제 내 low→high를 각각 정의해야 합니다.
세션 합성 집계와 설명 보완으로 이 경계를 남기고, 실제 사용자 재시도나 전환의 빈도가 검증되었다고 주장하지 않겠습니다.

## 후속 단계: 기존 도구의 지표 해석 정정

위의 ‘새 코드 없음’, ‘소스가 바뀌지 않아57검사를 다시 하지 않음’ 발언은 초기 토론 시점의 기록이다. 그 원문을 보존한 채, 이후 기존 도구에서 발견한 지표 해석 문제를 수정한 단계를 구분해 추가한다. 새 preflight를 만들지 않는 결정과 실제 모델·센서 실행을 하지 않는 결정은 유지했다.

**E → D: 후속 공유**

새 preflight 없음 결정은 그대로입니다.
다만 B/E가 발견한 현재 session_replay의 해석 문제를 기존 도구에서 바로 고치기로 했습니다.
legacy mode_switches는 보존하고 세션 인접 변경과 과제별 모드변경/low→high/추가제출, 같은 request의 추가 attempt를 분리하여 invalid semantics면 새 분석 지표를 null 처리합니다.
실제 코드변경에 필요한 최소 회귀검사·산출물 갱신과 B 독립 확인만 진행합니다.
D의 초기 ‘새 코드 없음’ 발언은 초기 토론 시점 원문으로 남기고 후속 기존코드 수정 단계를 따로 덧붙입니다.
고정점수·장비·모델·센서 증거는 갱신하지 않습니다.

**E → B: 정의 확인**

기존 request_id를 ‘서버가 수락한 하나의 논리 제출’로 사용합니다(새 user 재질문/재생성/모드변경은 새 request_id).
task_id는 고정 배정과제, attempt_id는 같은 request에 대한 개별 backend 실행이며 추가 attempt만으로 새 제출을 만들지 않습니다.
within_task_*는 세션 전체에서 각 task의 제출만 순서대로 모은 뒤 인접 mode 변화·low→high·첫 제출 이후 수를 합산합니다.
within_request_additional_attempts는 request마다 첫 attempt 이후 수를 합산하고, 실패원인이나 사용자 의도를 추정하지 않는 구조적 계수입니다.
새 유효5지표는 protocol_observation_valid가 false면 null, raw_event_metrics에는 감사 전 파서가 보존한 request/attempt 기반 계수를 남기며 legacy mode_switches/additional_requests는 기존 값을 유지합니다.
정상 로그에서 session_adjacent_mode_changes=mode_switches입니다.
