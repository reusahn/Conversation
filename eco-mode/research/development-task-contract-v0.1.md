# 개발용 과제 계약 v0.1과 수동 완성 정책

작성일 2026-10-28. A(HCI)의 공개 가상 검토에서 E(구현), B(논문), C(AI), D(운영)의 반론을 반영했다. 실제 전문가의 외부 심사나 참가자·모델·센서 결과가 아니다.

**이번에 고정한 것은 개발용 입력·출력 계약과 개발 정책이다.** 기존 `validation.js`의 T01–T04를 계보로 삼되 입력 범위를 제한한 별도 버전이다. 기존 일반 계약을 소급 변경하지 않는다. `contract_id=dev-task-contract-v0.1`, `bank_id=dev-public-bank-v0.1`을 제안하며 실제 manifest의 ID와 일치 여부는 구현 검토에서 확인한다. `final_human_bank_id=null`, `final_K=null`, `confirmatory_allowed=false`를 유지한다.

이 문서의 정수·ASCII 제한은 부동소수·Unicode·무제한 탐색의 모호성을 줄여 개발 채점의 참값을 확인하기 위한 선택이다. 인간에게 쉬운/어려운 과제, low 충분/불충분, high가 도움이 되는 과제라는 경험적 분류를 뜻하지 않는다. 실제 최종 과제집·숨김 bank·품질 허용폭·p_min·표본·시간한도는 동결하지 않았다.

## 1. 공통 데이터 계약

- 함수는 하나의 입력 배열을 받는 **동기 JavaScript 함수**이다. Promise·비동기 스트림은 이 개발 계약의 반환형이 아니다.
- 입력은 조밀한 ordinary array이다. 배열의 인덱스 누락, accessor, 추가 사용자 속성, 객체·순환 참조는 개발 bank에 넣지 않는다. T03/T04의 원소 배열도 해당한다. 이는 임의 악성 Proxy까지 판별하는 보안 명세가 아니다.
- 유한 수치 입력은 아래 범위의 JavaScript 정수만 허용한다. 합계가 Number의 정확 정수 범위에 충분히 들어가므로 임의 오차 허용치를 사용하지 않는다. 숫자 결과는 primitive number이며 수치가 정확히 같아야 한다. **+0과 -0은 같은 답으로 인정한다.** boxed number와 숫자 문자열은 정답이 아니다.
- 출력 배열의 writable/configurable 속성이나 이후 수정 가능성은 정답 조건이 아니다. 같은 조밀한 구조·값의 `Object.freeze` 출력도 정답으로 인정한다. 입력 bank 적합성 검사와 출력 기능 동치 검사를 혼동해 올바른 불변 출력을 기각하지 않는다.
- 입력 보존의 점수화 기준은 호출 전후의 깊은 구조·값이 같은 것이다. 외부 배열과 중첩 배열의 순서·길이·원소를 비교한다. 호출 중 일시적으로 변경했다가 복원하는 행위가 전혀 없었음을 이 snapshot 검사만으로 인증하지 않는다.
- 개발 bank는 공개 자료이다. 같은 함수를 여러 입력에 적용한 횟수를 사람 표본 수나 LLM 실행 수로 세지 않는다. 참조 함수의 통과만으로 scorer의 완전성이나 모든 오답 검출을 증명하지 않는다.
- 계약을 벗어난 fixture, 참조/oracle 오류, 손상·누락된 case 집합은 채점기 자료 문제로 처리한다. 후보 함수의 실패로 전가하지 않으며 **unknown/invalid-bank**로 남긴다. 빈 정상 입력과 비어 있는 채점 bank는 다르다. `[]`는 각 과제의 정상 입력이지만 case가 0개인 bank는 자동 전체통과하지 않는다.

## 2. T01 계열: `sumFiniteNumbers`

**입력:** 길이 0–32의 배열. 각 원소는 다음 중 하나이다.

- 포함 대상: 유한 정수 [-1000, 1000].
- 무시 대상: null, boolean, 길이 0–64의 아래 ASCII 문자열, NaN, +Infinity, -Infinity.

undefined, Symbol, BigInt, 객체, 유한 소수는 이 개발 입력 범위에 넣지 않는다. NaN/Infinity는 native JavaScript fixture 값이며 표준 JSON의 숫자로 직렬화할 수 있다고 가정하지 않는다. 텔레메트리 직렬화가 필요하면 별도 명시적 표현·복원 검증이 필요하다.

**출력:** 포함 대상만 더한 primitive number 정수. 빈 배열 또는 포함 대상이 없는 배열은 0. 허용 최대 절댓값은 32,000이므로 overflow·덧셈 순서 반올림 문제를 이 버전에서 제거한다. 입력은 호출 전후 그대로여야 한다.

**공개 예:** `[1, "2", false, null, NaN, Infinity, -1] → 0`. 문자열 "2"와 boolean을 숫자로 강제 변환하면 오답이다. `[1000, -1000, -0] → 0`이다.

기존 T01 일반 계약의 유한 소수 합계를 이 개발 버전에서 검사했다고 주장하지 않는다.

## 3. T02 계열: `normalizeTags`

**입력:** 길이 0–32 배열. 각 원소는 길이 0–64의 ASCII 문자열 또는 무시할 null·boolean·정수 [-1000,1000]이다. 허용 문자열 문자는 TAB(U+0009), LF(U+000A), CR(U+000D), printable ASCII(U+0020–U+007E)이다. VT/FF·비ASCII 문자는 이 버전에서 제외한다.

**변환 순서:**

1. 문자열만 남긴다.
2. 양 끝의 SP·TAB·LF·CR만 제거한다. 문자열 내부의 공백은 보존한다.
3. A–Z를 a–z로 바꾼다. 로케일 변환·Unicode 정규화는 추가하지 않는다.
4. 빈 문자열을 제외한다.
5. 변환 뒤 같은 문자열의 중복을 제거하되 처음 나타난 순서를 보존한다.

**출력:** 위 정규화 문자열의 조밀한 배열. 정렬하거나 첫 출현 순서를 바꾸면 오답이다. 입력은 호출 전후 그대로여야 한다.

**공개 예:** `[" B ", "a", "b", "\tA\r\n", null, " "] → ["b", "a"]`. `"a  b"`는 내부 공백 두 개를 보존한다. `[] → []`이다.

이 범위의 성공을 다국어 태그 정규화의 정확성으로 확대하지 않는다.

## 4. T03 계열: `mergeIntervals`

**입력:** 0–12개의 `[start,end]`. 각 끝점은 정수 [-100,100]이고 `start <= end`이다. 구간은 **닫힌 구간**이다. 점 구간 `[x,x]`, 중복 구간, 정렬되지 않은 입력을 허용한다.

**출력:** 합집합의 최대 연결 구간을 `[start,end]` 배열로 반환한다. 시작점 오름차순이고, 연결되는 구간은 모두 병합한다. 따라서 서로 인접한 출력 구간은 `previous_end < next_start`이다. 끝점이 같은 두 구간도 연결되어 병합한다. 닫힌 구간 사이의 양의 길이 빈틈은 메우지 않는다.

빈 입력은 빈 배열이다. 원소의 끝점·외부/중첩 배열을 호출 전후 보존한다. 출력은 exact primitive number endpoints를 가진 조밀한 길이2 배열들의 조밀한 배열이어야 한다.

**공개 예:** `[[10,12],[2,4],[4,10]] → [[2,12]]`; `[[0,0],[1,1]] → [[0,0],[1,1]]`. 후자는 정수 0과 1 사이의 실수 구간을 채우지 않으므로 병합하지 않는다.

## 5. T04 계열: `maxReward`

**입력:** 0–12개의 `[start,end,reward]`. 시작·끝은 정수 [-100,100], `start < end`, 보상은 정수 [0,1000]이다. 시간 구간은 **반열린 구간 `[start,end)`**으로 해석하므로 끝나는 시각과 다음 시작이 같으면 양립 가능하다.

**출력:** 서로 겹치지 않는 작업 부분집합의 보상 합계 최댓값인 primitive number 정수. 빈 부분집합을 허용하므로 빈 입력·모든 보상0은 0이다. 최대 합계는 12,000이다. 선택된 작업 목록·개수·일정을 반환하면 이 계약의 반환형이 아니다.

중복 작업도 별도 입력 레코드로 허용한다. 그러나 양의 길이인 동일 시간 구간은 서로 겹치므로 같은 시간의 중복 두 개를 함께 고를 수 없다. 가중치가 큰 긴 작업과 여러 짧은 작업의 경쟁을 허용한다. 입력은 호출 전후 보존한다.

**공개 예:** `[[0,1,1],[0,3,10],[1,3,1]] → 10`; `[[0,2,5],[2,4,6]] → 11`. 종료가 빠른 작업을 무조건 선택하는 greedy는 일반적으로 정답이 아니다.

개발 oracle의 부분집합 전수탐색은 입력12개에서 최대4096개 부분집합을 검토한다. 이것은 허용 범위에서 참값을 대조하기 위한 방식이며 참가자의 알고리즘을 전수탐색으로 제한하지 않는다.

## 6. 수동 완성 정책 — 개발 버전에서 선택한 공통 규칙

다음 규칙은 개발용 작업 흐름에서 선택한 정책이다. 실제 참가자 화면·동의·집행·이해도·Tmax·채점 격리까지 검증한 최종 사람 정책은 아니다. 목표 사용자 후보는 **기초 JavaScript 함수를 읽고 수정할 수 있는 사람**이며, 모집·대표성·타당화는 미정이다.

| 항목 | 선택한 개발 정책 |
|---|---|
| 직접 작성·수정 | 허용한다. AI를 한 번도 호출하지 않은 완성도 같은 최종 기능 기준으로 채점한다. |
| 편집 환경 | 연구 앱의 과제별 편집기에서 한 동기 함수의 산출물을 관리한다. 실제 앱 구현 완료를 뜻하지 않는다. |
| 복사/붙여넣기 | 앱이 제공한 AI 응답·starter·공통 고정 문서의 내용을 편집기에 옮기는 것은 허용한다. 외부 코드·개인 답안의 가져오기는 허용하지 않는 후보 정책이다. |
| 웹·외부 AI·라이브러리 | 외부 AI·웹 검색·패키지 설치·개인 코드 저장소 접근은 허용하지 않는다. 모든 집단에 같은 버전의 고정 JavaScript 설명 문서만 제공하는 후보를 택한다. 실제 준수 확인·위반 판정·사용성은 검증하지 않았다. |
| 허용 구현 | 공통 runtime의 표준 JavaScript 기능을 사용할 수 있다. import, 파일·네트워크·프로세스 접근은 과제에 필요하지 않으며 허용 구현 범위에 넣지 않는다. 이 문구가 실행 격리를 구현하지는 않는다. |
| 수행 중 피드백 | 별도 공개 feedback bank의 기능 결과만 제공한다. 실행 횟수·표시·비용 정책은 집단 공통으로 동결해야 한다. 공개 개발 bank와 최종 숨김 bank를 동일시하지 않는다. |
| 제출·재편집 | 전체 세션 잠금 전에는 과제별 재편집·재제출을 허용한다. 각 과제의 마지막으로 확정 제출된 불변 스냅샷을 사용한다. 미확정 편집 버퍼나 잠금 뒤 응답으로 제출물을 구제하지 않는다. |
| 잠금 뒤 | 숨김 연구 채점은 잠긴 산출물에 읽기전용으로 적용한다. 그 결과를 본 뒤 수정하거나 좋은 답으로 스냅샷을 교체하지 않는다. |
| 무AI 완성 | `mode=none`과 성공이 함께 존재할 수 있다. 호출0을 실제 미시작·품질실패로 바꾸지 않는다. 할당된 세션의 유휴 에너지는 기존 계측 경계에 남긴다. |
| 실패·누락 | 건강한 scorer에서 계약 불충족이 확인되면 관측 실패이다. scorer/oracle/인프라 고장·미귀속 timeout·산출물 유실은 unknown으로 구분한다. |

실제 시간한도·시작/포기 사건·참가자별 시행 규칙은 여전히 미정이다. 기술 개발의 임의 timeout을 참가자의 과제 시간한도나 품질 실패 기준으로 승격하지 않는다. 연구용 사후 채점의 에너지는 별도 보고하고, 과제 수행 중 backend의 운영상 공개 검증은 기존 세션 에너지 경계에 포함한다. 공개 검증과 사후 채점을 이중 합산하지 않는다.

## 7. 난도·충분성과 고정 점수

구조적 복잡도, 사람이 느끼는 난도, low의 성공률 문턱 충족, high의 실제 유효성은 서로 다르다. low가 실패한다고 high가 유효한 것은 아니다. 두 모드의 독립 자료·동시 불확실성·사전 p_min에 따른 별도 분류가 필요하며, 이 개발 bank의 oracle·오답 검사는 그 자료가 아니다. high 문턱 충족과 low 대비 의미 있는 향상폭도 별도 주장이다.

기존 A92, B62.5, C설계100, D73, E설계97/실행50 점수를 이 문서 작성만으로 올리지 않는다. 개발용 계약의 일부 미정을 선택했지만, 최종 과제와 독립 타당화·실용 δ·실제 구현/계측·최종 표본 근거의 결손은 남는다. 실제 코드에서 본 계약과 다르게 구현된 부분은 검토 결과에서 별도로 표시해야 한다.
